How to get your TOTP seed

            
          

          

            Follow these steps on your test account to extract the TOTP secret that bc-replay uses to auto-generate one-time passwords.
            You only need to do this once per account.  
            Open full guide
          

          
    
            
  1. 
              Go to account.microsoft.com/security
              and click Add a new way to sign in or verify.
              
            
    2. 
            
  2. 
              Choose Use an authenticator app, then click Set up a different authenticator app.
              
            
    3. 
            
  3. 
              On the QR code screen click I can't scan the QR code.
              
            
    4. 
            
  4. 
              Copy the Secret key — this is your TOTP seed. Paste it into the MFA seed field above.
              Also note the Account name for the next step.
              
            
    5. 
            
  5. 
              On your phone: open Microsoft Authenticator → add account → choose Other account (Google, Facebook, etc.).
              When prompted, choose Enter manually (or OR code if you prefer).
              
            
    6. 
            
  6. 
              Enter the account name and paste the secret key from step 4.
              
            
    7. 
            
  7. 
              The account now appears in your authenticator app — confirm it looks correct.
              
            
    8. 
            
  8. 
              Back in the browser, enter the 6-digit code currently shown in the app.
              
            
    9. 
            
  9. 
              Done! When prompted, set this as your default sign-in method.
              
            
    10. 
          

          

            Tip: bc-replay re-generates the 6-digit OTP automatically during test runs — no manual entry needed once the seed is saved here.

Tips & Tricks

      


      
A curated collection of best practices for building reliable BC page scripts and multi-step workflows. Sourced from official Microsoft documentation and hands-on project experience.


      
      

        
🎬 Recording Best Practices

        
    
          
  • Start from a well-known page. Always begin recording from the Role Center or a predictable starting point — playback starts from the current page.
    • 
          
  • Create new entities for tests. Create a new customer, vendor, or item specifically for the test rather than relying on data that may not exist during playback.
    • 
          
  • Filter grids before selecting. When selecting a value in a list or grid, filter it so the desired value appears first. This avoids fragile row-index dependencies.
    • 
          
  • Keep recordings small and focused. Divide large processes into smaller scripts (e.g. setup user → create customer → create order → post order). Smaller scripts are easier to maintain and debug.
    • 
          
  • Avoid multi-line selections. If you select multiple records in a list during recording, only the last selection is captured. Use individual steps instead.
    • 
          
  • Don’t depend on volatile data. Avoid relying on dates, auto-numbers, or other data that changes between runs. Use parameters or expressions instead.
    • 
        

      


      
      

        
📝 YAML Script Structure

        
    
          
  • Never manually craft YAML from scratch. Always record a BASE script in BC first, then edit only the values you need to change. The YAML format must match what BC’s recorder produces exactly.
    • 
          
  • Preserve runtimeRef values. These are generated during recording and identify page instances. Changing them breaks playback.
    • 
          
  • Understand the action types. Common types are input (set field value), invoke (click action/button), focus (move to a control), navigate (open page), and set-current-row (move to next line in a repeater).
    • 
          
  • Use the description field. Each step has a description that documents what the step does. It’s useful for debugging but doesn’t affect playback.
    • 
          
  • Handle optional pages. If a confirmation dialog or other page may or may not appear, mark it as optional in the recording. Otherwise playback fails when the page doesn’t show.
    • 
        

        

          
Example: Header field input

          
- type: input
  target:
    - page: Purchase Order
      runtimeRef: b385
    - field: Buy-from Vendor No.
  value: "1000"
  description: Input <value>1000</value> into <caption>Vendor No.</caption>

        

        

          
Example: Line entry (repeater)

          
- type: focus
  target:
    - page: Purchase Order
      runtimeRef: b385
    - part: PurchLines
    - page: Purchase Order Subform
    - repeater: Control1
    - field: No.
  description: Focus <caption>No.</caption>
- type: input
  target:
    - page: Purchase Order
      runtimeRef: b385
    - part: PurchLines
    - page: Purchase Order Subform
    - repeater: Control1
    - field: No.
  value: "1896-S"
  description: Input <value>1896-S</value> into <caption>No.</caption>

        

      


      
      

        
🔧 Parameters & Expressions

        
    
          
  • Parameterize variable values. Instead of hardcoding customer numbers, item IDs, or dates, define parameters so the same script can be reused across scenarios.
    • 
          
  • Use Power Fx expressions. Property values support Power Fx — for example "Customer " & Today() generates a dynamic name, and Clipboard.'Field' + 1 validates an incremented value.
    • 
          
  • Pass parameters between scripts. When using “Include a script” to chain recordings, define matching parameters in both the host and included scripts to share values.
    • 
          
  • Reference session info. Use Session.'User ID' in expressions to filter lists by the current user or fill in user-specific fields dynamically.
    • 
        

      


      
      

        
✅ Validation & Conditional Steps

        
    
          
  • Add validation steps. Right-click a control during recording and select Page Scripting > Validate > Current Value to assert expected outcomes. This turns scripts into real tests.
    • 
          
  • Use clipboard for cross-step validation. Copy a value from one control, then validate it in another using the clipboard reference.
    • 
          
  • Make steps conditional. Use Add conditional steps when to handle branches — e.g. only run cleanup steps when a list has rows.
    • 
          
  • Add wait steps strategically. Insert wait steps after actions that trigger background processing (like posting) to give BC time to complete before the next step.
    • 
        

      


      
      

        
⬡ Workflow Design Tips

        
    
          
  • One process per project folder. Keep each business process (PO creation, approval, posting) in its own folder with its own BASE script, data files, and variants.
    • 
          
  • Chain scripts with “Include”. Break large flows into reusable building blocks and include them in a master script. This allows parallel development and easier debugging.
    • 
          
  • Set field dependencies in order. Some fields are only visible after other fields are set. For example, Location Code requires Ship-to option set to “Location” first.
    • 
          
  • Use multi-user workflows for approval scenarios. Define roles (Creator, Approver) with separate credentials. Each step in the workflow can run under a different user.
    • 
          
  • Test the BASE script first. Always validate the BASE recording works end-to-end before generating variants or building a workflow around it.
    • 
        

      


      
      

        
⊞ Variant Generation

        
    
          
  • Validate data files against BC. Items, Locations, and Vendors listed in your data files must exist in the target BC company. Missing data = silent failures.
    • 
          
  • Use consistent naming. Data files should use the expected names (Items, Locations, var-vendors) — one value per line, no headers.
    • 
          
  • Generate a single variant first. Verify substitution works correctly before generating the full combinatorial suite.
    • 
          
  • Only substitute variable fields. The generator should replace specific field values, not modify the YAML structure. Any structural changes should go back into the BASE script.
    • 
        

      


      
      

        
▶ Running & Debugging

        
    
          
  • Use -Headed mode for debugging. Add the -Headed flag to see the browser during playback. This makes it easy to spot where scripts fail.
    • 
          
  • Check permissions. The BC user needs PAGESCRIPTING - PLAY permission set (and PAGESCRIPTING - REC for recording).
    • 
          
  • Disable MFA for test accounts. The bc-replay player uses AAD authentication with username/password only — it does not support multi-factor authentication.
    • 
          
  • Never store passwords in files. Use environment variables or the Windows Credential Manager. Prompt for passwords securely with Read-Host -AsSecureString.
    • 
          
  • Review the Playwright report. After a run, use npx playwright show-report to see detailed results, screenshots, and timing for each step.
    • 
        

      


      
      

        
🔄 Pipeline & CI/CD Integration

        
    
          
  • Prerequisites: Node.js 16.14+ and PowerShell 7+ are required on the build agent.
    • 
          
  • Install bc-replay: Run npm i @microsoft/bc-replay --save in your pipeline’s working directory.
    • 
          
  • Pass credentials via environment variables. Set BC_USERNAME and BC_PASSWORD as secret pipeline variables, then reference them with -UserNameKey and -PasswordKey.
    • 
          
  • Run all scripts with a glob: Use npx replay .\recordings\*.yml to execute every script in a folder.
    • 
          
  • Publish test results. The result folder contains JUnit XML — publish it to your CI system for trend tracking.
    •
