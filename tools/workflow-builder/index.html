BC Workflow Builder

The BC Workflow Builder is a visual tool for composing multi-user Business Central test workflows — without editing JSON by hand. You wire together recorded .yml page scripts, define who runs each step, and let the tool export the files that Run-BCWorkflow.ps1 needs to execute the full workflow.

What problem does it solve?

Business Central processes often span multiple users — a purchaser creates a PO, an approver reviews it, finance posts it. Each individual action can be recorded as a .yml script using BC's page scripting recorder. The Workflow Builder stitches those individual scripts into a single, reproducible workflow where data automatically flows between steps.

Core concepts

ConceptWhat it means
ProjectA named folder under page-scripting/ that holds your workflow, scripts, and user templates.
StepOne script execution by one user, with optional input/output values.
CaptureA value read from BC during a step (e.g. the PO number just created) and stored for later steps.
InjectA captured value from a previous step injected into the current step's script parameters.
User RoleA named actor (purchaser, approver) mapped to real BC credentials in users.json.
This tool is for demo and research purposes. Use at your own risk in non-production environments.

Quick Start

Get from zero to a running workflow in under 10 minutes.

Prerequisites

  • The local app server is running (start.ps1 or start.bat from the repo root).
  • You have at least one recorded .yml page script from BC's page scripting recorder.
  • Test user accounts exist in your BC environment with MFA disabled.

Step-by-step

  1. 1Open the builder — navigate to http://localhost:3000 (or open index.html directly in a browser).
  2. 2Select an environment on the project picker screen or pick an existing project.
  3. 3Fill in Workflow Settings — give your workflow a name and confirm the BC URL (left sidebar).
  4. 4Upload scripts — drag .yml files onto the Script Library drop zone.
  5. 5Add steps — click + Add Step, choose a role and assign a script for each step.
  6. 6Review captures & injects — check the auto-suggested values in the Step Properties panel.
  7. 7Save or Export — use Save to write back to the project folder, or Export JSON to download the files.
  8. 8Run the workflow — open a terminal in bc-replay/ and run .\npx-run.ps1.
Always test your BASE scripts manually in BC before adding them to a workflow. A script that fails on its own will fail in the workflow too.

Workflow Settings

The left sidebar contains the global settings that apply to the whole workflow.

Name

A human-readable label written into workflow.json as the name field. Used in test reports.

Description

Optional free-text description of what the workflow tests. Stored in workflow.json.

Environment

Select the BC environment from the drop-down. This auto-populates:

  • The BC Environment URL field.
  • Available user roles (fetched from the project's users.json).

BC Environment URL

The full URL passed to npx replay as the -StartAddress parameter. Example:

https://businesscentral.dynamics.com/your-tenant-id/sandbox
If you change the URL after steps have been added, make sure your scripts are still valid for the new environment and company.

User Roles

Roles represent the different actors in your workflow. Each step is executed by exactly one role.

How roles work

When you select an environment, roles are loaded automatically from the project's users.json file. Each role gets a unique colour that appears in the swim-lane headers and on step cards so you can quickly see who does what.

Role colours in the canvas

The canvas uses swim lanes — one column per role. Steps are placed in the lane of whichever role is assigned to that step, making the handover between users immediately visible.

users.json format

{
  "purchaser": { "username": "purchaser@tenant.onmicrosoft.com", "password": "secret" },
  "approver":  { "username": "approver@tenant.onmicrosoft.com",  "password": "secret" }
}
Never commit users.json with real passwords to version control. Use users.sample.json as a template and add users.json to .gitignore.

Script Library

The Script Library holds the .yml page scripts that you assign to workflow steps.

Adding scripts

  • Drag & drop — drag one or more .yml files from your file explorer onto the drop zone.
  • Click to browse — click the drop zone to open a file picker.

Removing a script

Click the × button on any script chip. If a step is already using that script, the script reference on that step will be cleared.

Upload all scripts for the workflow before building steps — the auto-suggest for captures and injects only works if the source script is already in the library.

Workflow Steps

Steps are the individual script executions that make up your workflow, shown as cards in the canvas.

Adding a step

Click the + Add Step button at the bottom of the canvas. A new card appears and the Step Properties panel opens on the right.

Step card anatomy

PartDescription
Role badgeColoured label showing which user runs this step.
Step nameDisplay name — defaults to the script name, fully editable.
Step IDMachine-readable identifier used in depends_on references.
Script pathRelative path to the .yml file.
captureNumber of values captured from BC during this step.
injectNumber of captured values injected into this step's parameters.

Step dependencies

Each step has a depends_on field. By default a new step depends on the previous step, ensuring correct execution order. You can change this in the Step Properties panel — useful for parallel steps or workflows that branch.

Reordering steps

Delete a step and re-add it in the correct position, or adjust depends_on to control the logical execution order.

Deleting a step

Open the step's properties panel and click Delete Step at the bottom.

Click any step card to open its properties. The canvas supports horizontal scrolling if you have many roles or many steps.

Captures & Injects

Captures and injects are how data flows between steps — for example, passing the PO number created in step 1 to the approver script in step 2.

Captures

A capture reads a value from BC during step execution and stores it under a variable name. In your .yml script, a capture looks like this:

- type: copy-value
  source:
    - page: Purchase Order
    - field: No.
  name: po_number

The builder detects these automatically when you load a script. In Step Properties you will see auto-suggested capture entries. Accept them with one click.

Injects

An inject takes a captured value from an earlier step and passes it to a parameter in the current step's script. The script must declare the parameter in its parameters: section.

parameters:
  po_number:
    default: ""

The builder matches inject targets to available captures from all preceding steps and suggests mappings automatically.

Manual entries

You can add capture/inject rows manually using + add row in the Step Properties panel if the auto-detection misses something.

ColumnDescription
Key (capture)Variable name stored in workflow state.
Field / Path (capture)BC field to read the value from (e.g. No. or a JSONPath like $.id for API steps).
Parameter (inject)Script parameter name to receive the value.
From (inject)Variable name produced by the capture in the earlier step.
Capture variable names must be unique across the entire workflow. If two steps capture to the same name, the later value overwrites the earlier one.

API Steps

API steps call a BC REST endpoint directly (without a page script), useful for data setup, validation, or triggering background processes.

Adding an API step

In the left sidebar under API Components, click a component chip or drag it onto the canvas. A new step card with a purple API indicator is added.

Available components

ComponentDescription
BC API CallGeneric REST step — configure method, endpoint, and body yourself.
Create CustomerPOST to the 4PS custom /customers endpoint. Body and response capture are pre-filled.

API step properties

  • Method — GET, POST, PATCH, DELETE.
  • Endpoint — full URL; supports {{tenantId}}, {{environmentName}}, {{companyId}} tokens.
  • Body template — JSON body sent with POST/PATCH requests. Values can reference injected captures with {{variable_name}}.
  • Capture response — JSONPath expressions mapping response fields to capture variables (e.g. $.id → customer_id).
  • App registration — select which OAuth credentials to use for authentication.

API steps run in a dedicated system swim lane (created automatically) and do not require a user role.

API steps require a configured App Registration. Import your app-registrations.json before running a workflow containing API steps.

App Registrations

App registrations provide the OAuth client credentials used to authenticate API steps against BC.

Importing

Click Import next to the App Registrations heading in the sidebar and select your app-registrations.json file. The builder parses and stores the registrations for the current session.

File format

{
  "my-app": {
    "client_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "client_secret": "your-secret-here",
    "tenant_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
    "environment_name": "sandbox",
    "company_id": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
  }
}

Use app-registrations.sample.json as a template and never commit your real app-registrations.json to version control.

Assigning to an API step

In the Step Properties panel for an API step, select the desired registration from the App Registration drop-down. The tenant ID, environment name, and company ID are automatically substituted into endpoint URL tokens.

The app registration must have Financials.ReadWrite.All (or the relevant BC API permission) granted in Microsoft Entra ID.

Export & Save

Two ways to get your workflow out of the builder and into the file system.

Save (recommended)

Click Save in the header. This writes workflow.json and users.sample.json directly back to the current project folder on disk. Requires the local app server to be running.

Export JSON

Use the validation & export flow (available if the builder shows an Export button, or via keyboard shortcut) to download both files to your browser's Downloads folder. Move them into your project folder manually.

Validation before export

Before saving or exporting, the builder runs automatic validation and will show an error list if anything is missing:

  • Workflow name is required.
  • Every step must have a role and a script assigned.
  • Step IDs must be unique.
  • A BC Environment URL must be set.

After exporting

  1. Copy users.sample.json to users.json and add real credentials.
  2. Place your .yml script files in the scripts/ sub-folder alongside workflow.json.
  3. Run the workflow from bc-replay/: .\npx-run.ps1
After running, open the HTML report with npx playwright show-report inside the bc-replay/ folder.

Output Files

The builder produces two files consumed by Run-BCWorkflow.ps1.

workflow.json

{
  "name": "Purchase Order Approval",
  "description": "End-to-end PO creation and approval",
  "bc_url": "https://businesscentral.dynamics.com/tenant/sandbox",
  "steps": [
    {
      "id": "create-po",
      "name": "Create Purchase Order",
      "user": "purchaser",
      "script": "./scripts/create-po.yml",
      "capture": { "po_number": "No." }
    },
    {
      "id": "approve-po",
      "name": "Approve Purchase Order",
      "user": "approver",
      "script": "./scripts/approve-po.yml",
      "depends_on": "create-po",
      "inject": { "po_number": "po_number" }
    }
  ]
}

users.sample.json

{
  "purchaser": {
    "username": "purchaser@yourtenant.onmicrosoft.com",
    "password": "your-password-here"
  },
  "approver": {
    "username": "approver@yourtenant.onmicrosoft.com",
    "password": "your-password-here"
  }
}

Copy to users.json and fill in real credentials. This file is for the current workflow project only.
